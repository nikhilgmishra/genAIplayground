# calls/binding: CallBinding issuance, recovery and the media-path control plane (WP-11)

The trusted half of the media path. The conversation runtime (`media/`, LiveKit Agents worker) never constructs a
binding, a session reference or a generation: it asks the gateway's media routes
(`platform/src/gateway/http/media-routes.ts`) and this service answers.

| File | Purpose |
|---|---|
| `service.ts` | `CallBindingService`: `bind` (first owner: start the session; recovery: re-bind with a new generation and fencing token, void the old owner's pending actions; refuses another room's carrier, another room instance or name, a gone or rewritten carrier party), `heartbeat`, `lifecycle` (party change, hold, transfer leg, hang-up), `consentDecision` (decline or revocation from the media path, the RECORDING_REFUSED injection point), `reportProcessing` (readout judged by the consent the owner was last told; the answer carries the current directive; a mismatch routes to a person), `resolveClaim` (in-process bearer session for runtime tool calls, WP-14), `interactionForRoom` (session-less human and safety routes, SAFE-02), `endRoom` (the supervisor's end of a call whose caller left), `recordersOfJob` (the call's named recorders and directive for a runtime refused into a person route: job-checked like a bind, issues nothing; a reported flag is recorded on the call and audited, DATA-03) |
| `store.ts` | `CallBindingStore` over a conditional key-value store (DynamoDB in live compositions): the room's person request (room server id -> standard and safety requests, OUTSTANDING or ACCEPTED; compare-and-swap), the room claim (room server id -> interaction, carrier, carrier party digest; first writer wins), the carrier index (carrier interaction -> interaction and the claiming room; first writer wins, another room refused) and the call record (compare-and-set), created under a first-bind lease (one request per call starts the session, so a concurrent first bind, e.g. a worker's retry of a bind whose answer it lost, never supersedes the session the record names; it is refused retryably with BINDING_CONCURRENT_UPDATE). The room name and the SIP party identity are kept as SHA-256 digests; the session reference is sealed (AES-256-GCM, AAD bound to tenant and interaction) |
| Person requests | `roomForRoute` (the room of a session-less route: MEDIA_ROOM_NOT_FOUND refused; an unreachable media plane gives a fresh, unattributed interaction), `notePersonRequested` / `notePersonAccepted` / `notePersonAttemptEnded` (the room's person request, written before the handoff is attempted, with an attempt lease so one handoff is in flight per room: a concurrent request is answered HANDOFF_IN_PROGRESS by the router; a handoff the HandoffService could not place, the next-route prompt with no journey, is answered HANDOFF_NOT_PLACED and the room stays owed), `personStateOfRoom` (NONE, OUTSTANDING, WITH_PERSON). Every `bind` reads it before and after its write (a request that appeared in between revokes the binding just written): a person owed is refused BINDING_PERSON_REQUESTED, a person on the call BINDING_WITH_PERSON; a recovery (or the owner's own retry) whose consent sends the caller to a person is refused BINDING_CONSENT_REQUIRES_PERSON before the generation moves. A live binding is held to it too: every `heartbeat` reads the request and is refused the same way, and the `lifecycle` and `reportProcessing` answers carry it (`routeToHuman` with that reason code; the facts are recorded either way), so a person requested by anyone reaches the owner within one heartbeat interval; the runtime tool path (WP-14) resolves a claim through `resolveClaimForAiAction`, which refuses the same way, so no AI action lands on a call that went to a person. Issuance and recovery evidence: `issuanceAudit` (PENDING, WRITTEN, MISSING) on the call record; the owner's retry writes a missing event before it is answered. Recorders: the egress ids the owners reported (`recorders`), returned to the next owner as `adoptableRecorders` |
| `livekit-lookup.ts` | `LiveKitCarrierLookup`: verifies with livekit-server's own Twirp API that the job was dispatched to and assigned to that agent in that room and that the agent is present; returns the room facts (server id, active SIP parties earliest first with their `sip.callID`, identities only as digests, never the caller number). Accepts the proto field names livekit-server emits (`agent_dispatches`) |
| `supervisor.ts` | `MediaPlaneSupervisor`: one sweep per interval over livekit-server's own state (rotating windows of `maxRooms`); re-dispatches a room whose caller is still connected while no agent holding one of its jobs is (livekit-server does not move a dead worker's job), routes the caller to a person after a deadline without a stable runtime (retried every sweep until it succeeded; `supervisorHumanRoute` in `gateway/http/media-routes.ts`, a fresh interaction when the media plane cannot name the room), and ends the call of a room whose caller left (`supervisorEndCall`). Before it re-dispatches it reads the room's person request (`supervisorPersonState`): a person owed is routed every sweep instead (the AI is never re-dispatched), a caller with a person is left alone (WITH_PERSON), and a request that cannot be read is PERSON_STATE_UNKNOWN: never re-dispatched, the orphan clock runs and the caller is routed once at the deadline |
| `runtime-auth.ts` | `RuntimeCredentialVerifier`: the conversation runtime's OAuth access token (issuer, audience, scope, client allowlist; JWKS through the egress transport in live compositions). No fixture or development mode |
| `ports.ts` | Structural ports (the calls module may import only audit, db, observability, protocol and shared): conditional KV, call session, carrier lookup, sealer, pending-action invalidator, audit sink |

Trust boundary: the media worker holds the media-plane API secret (Agents registration), and LiveKit keys cannot be
scoped, so participant kinds and attributes (`sip.callID`) are facts about a room, never proof of a call. One call
lives in one room: pinned at the first touch, compared on every bind (`docs/adr/proposed/WP-11-livekit-media-runtime.md`
decision 3; threat rows T-FO-11-01 and T-FO-11-09).

Invariants: AUTH-03 (claims are copied from the gateway; every request is checked against the stored binding, its
generation and its fencing token; a stale or forged claim is a 409; a carrier reference never names a second room), DATA-03 (`permittedTaps`: UNKNOWN is not
consent; a decline from the media path outranks the stored grant for the rest of the call; the consent version is
monotonic), SAFE-02 (human and safety routes need no binding or session; a caller owed or with a person is never handed back to
the AI), OPS-01 (issuance fails closed when its audit event cannot be written, and the retry writes the missing event
before it is answered; a decline is applied even then).

Composition (WP-17, `platform/src/main/**`): see the wiring hand-off of WP-11 (the CallBindingStore on its own
DynamoDB table, a dedicated sealer key, the LiveKitCarrierLookup over the container's egress transport with the LiveKit
API secret from the SecretResolver, the RuntimeCredentialVerifier with `transportJwksResolver`, and
`registerMediaRoutes` on the gateway app).

Tests: `service.test.ts`, `store.test.ts`, `livekit-lookup.test.ts`, `supervisor.test.ts`, `runtime-auth.test.ts` (unit,
labelled unit fakes for the media plane); `platform/test/integration/media` (Layer 2: DynamoDB Local, livekit-server,
Keycloak, the live composition; `carrier.test.ts` forges and rewrites `sip.callID` with the API secret).
