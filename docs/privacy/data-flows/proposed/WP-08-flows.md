# WP-08 data-flow rows (draft, phase C): model requests, catalogue listings, emulator and cassettes

Drafted by WP-08 for the flows it adds or changes; the phase C data-flows owner (WP-17) merges them into
`docs/privacy/data-flow-inventory.md` (rows DF-27 onwards use the two status axes). They implement the adapter side of
DF-32 (text model endpoints) and TDF-03; the scope of what a model receives (masked ContextSnapshot, permitted tools) is
WP-10 and WP-24.

Implemented and exercised against the protocol emulator only (SYNTHETIC data). No real provider has been called.

| ID | Flow | Data | Source -> destination | Storage and protection | Access | Retention / deletion | Logs and metrics | Status |
|---|---|---|---|---|---|---|---|---|
| DF-WP08-01 | Model inference request and stream | Instructions (pinned prompt template), the turn's messages, tool results and tool schemas; most sensitive class declared per request and checked against the endpoint's own `maxDataClass` before any I/O (PHI only to an endpoint whose ceiling allows it AND a covered, approved model-class destination; never VERIFICATION_SECRET) | Conversation runtime (harness, WP-10) -> `ResilientModelPort` -> provider adapter -> egress-classified transport -> OpenAI Responses, Bedrock ConverseStream or a private vLLM server | TLS to the exact allowlisted host, DNS answers checked and pinned, per-request model egress check of provider, region and retention terms; OpenAI requests with `store: false`; the response is held in process memory for the turn only | Model endpoint credentials as opaque handles from the composition root (Secrets Manager reference or the Bedrock task role); never logged | Provider-side retention per the endpoint's approved terms (AIN-49, UNKNOWN until recorded); nothing persisted by the adapter | Content-free: `vsp_model_calls_total{provider,outcome}`, `vsp_model_call_latency_ms`, `vsp_model_tokens_total{provider,direction}`, `vsp_connector_http_requests_total{dependency="model-provider"}`, `vsp_egress_denied_total{reason}`; logs carry outcome and reason codes only | Software `VERIFIED_LOCAL` (WP-08, emulator); environment `NOT_CONFIGURED` (AIN-02, AIN-26, AIN-49) |
| DF-WP08-02 | Model invocation audit metadata | Registry entry reference, revision, endpoint and region, pins, the keyed HMAC-SHA256 digest and the class of the input, tool scope, budget, typed outcome, provider-reported tokens and cost; `contentRecorded: false` | Model port caller -> `modelInvocationRecord` -> the audit writer of the composition owner | No prompt or completion text; the digest is keyed with the audit or tenant digest key (at least 32 bytes, held by the composition root), so a low-entropy prompt cannot be confirmed by hashing guesses; a record exists for every call whose request bytes reached or may have reached the allowlisted endpoint (`sentAttempts >= 1`, whatever the outcome, including a 401/403 after send and a barge-in after send: the count waits for the in-flight attempt to settle and counts one still open as sent) with a class its egress check allows; the recorded budget is the one the call ran with (capped at the endpoint ceiling), and never for a call refused before any byte was sent (`endpointAllowlisted: true` is never claimed for a refused call) | Audit readers (WP-04) | Audit retention | Reason codes only | Software `IMPLEMENTED` (WP-08 builder; persisting it is WP-10/WP-17) |
| DF-WP08-03 | Provider catalogue snapshot | Model ids, publisher owner names, lifecycle, modalities, `max_model_len`, the sorted-id digest, the count of account-scoped models, capture date, endpoint reference and region; no conversation data (class INTERNAL). Never account identifiers: an owner naming an account (`org-`, `user-`, `proj_`, a digit run) is recorded as `ACCOUNT_SCOPED`; a fine-tuned id or an ARN with an account id is recorded as `account-scoped:<HMAC-SHA256 prefix>` under the catalogue digest key (`--digest-key-file`, owner-only) or a random per-snapshot key that is never stored (`accountScopedIdDigest`: KEYED or EPHEMERAL), so the account id cannot be recovered by enumeration | Discovery command -> provider listing API (`/v1/models`, Bedrock `/foundation-models`, SigV4) -> a dated JSON file in the operator's `--out` directory | File on the operator workstation or the qualification runner | Operators preparing registry pins (WP-09) and release manifests (WP-40) | Kept with the release evidence | Content-free | Software `IMPLEMENTED` (WP-08); environment `NOT_CONFIGURED` (AIN-26) |
| DF-WP08-04 | Real-model local profile check | The synthetic connectivity prompt of the profile (no caller data, class INTERNAL) and the model's synthetic reply (only its length is printed) | Developer workstation -> reviewed provider endpoint or licensed local vLLM server | Credential from an environment variable or an owner-only file, never written by the command | The developer holding the reviewed credential | Provider terms of the reviewed account; nothing stored locally | Status JSON with reason codes | Software `IMPLEMENTED` (WP-08); environment `NOT_CONFIGURED` (AIN-26, AIN-28, AIN-30) |
| DF-WP08-05 | Emulator request log and recorded cassettes | Emulator: method, path, host, model id, authorization and signature result, stream and `store` flags, counts (no bodies); cassettes: response bytes of SYNTHETIC exchanges and the SHA-256 of each request body, no request header | Tests -> `model-emulator` (local Layer 2) or the in-process emulator; recording -> `platform/test/emulators/models/recordings` | Emulator memory (per host, until forgotten or restart); cassettes committed, synthetic only (recording refuses other classes) | Local developers and CI | Emulator: process lifetime; cassettes: repository history | None | Software `VERIFIED_LOCAL` (WP-08) |
