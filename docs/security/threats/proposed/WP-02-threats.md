# WP-02 proposed threat rows: contract registry boundary

Drafted by WP-02 (contract registry) for the phase B threat-model owner to merge into
[`docs/security/threat-model.md`](../../threat-model.md) (ownership rule "Threat rows" in
`docs/followon/work-packages.yaml`). Row ids are provisional (`T-FO-02-nn`); the merging owner assigns
the next `T-` numbers. Columns follow the threat model's main table.

| ID | Threat | STRIDE | Attack path | Mitigation | Enforcement location | Test tags | Residual risk | Status |
|---|---|---|---|---|---|---|---|---|
| T-FO-02-01 | Identity or scope injected through a proposal | S, E | A model output, caller utterance, retrieved document or vendor tool argument proposes `tenantId`, `actorId`, `subjectId`, `selectedRole`, `assurance`, `consent`, `permittedScopes`, `sessionGeneration` or a trusted envelope field (`actorRef`, `subjectRef`, `interactionId`, `causationId`, `schemaVersion`, `processingBasis`), possibly nested or array-wrapped | `ModelDecision.arguments` and `ToolRequestV2.arguments` refuse every `PROPOSAL_FORBIDDEN_FIELDS` name at any depth (depth bound 8; deeper is refused) in any spelling (case-insensitive, `_` and `-` ignored, so `tenant_id`, `TenantId` and `ASSURANCE` are refused) AND every key one of whose words names an identity, authority or consent concept (`PROPOSAL_FORBIDDEN_CONCEPTS`: `role`, `subject`, `consentRecording`, `consent_automated_processing`, `scopes`, `verified`, `callerRole`, `recordingconsent`), with one reviewed value-bound exemption (`concernSubject` = SELF/THIRD_PARTY/UNKNOWN, the safety tool argument), scanning the raw value before parsing, with key-count and size bounds; trusted contracts (`AuthContext`, `CallBinding`, `ToolRequestV2.tenantId`) are populated only by trusted components; `ModelDecision.authority` is the literal `PROPOSAL_ONLY` | `platform/src/protocol/common.ts` (`findForbiddenProposalField`, `safeParseUntrusted`), `models.ts` (`ProposedArguments`), `tool-envelope.ts` (`BoundedToolArguments`) | AUTH-03 (`protocol/auth03.test.ts`) | Enforced only where the producer parses the follow-on schema: the gateway still serves the original `ToolRequest` until the registry owner adopts `ToolRequestV2` (WP-07); the harness (WP-10) must parse model output with `ModelDecision`. The concept scan works on English key words: an identity field named in another language, or as an unrelated word, is caught only by the target tool's strict input schema | IMPLEMENTED (contract); adoption pending WP-07, WP-10 |
| T-FO-02-02 | Prototype pollution through untrusted JSON | T, E | A JSON body carries `__proto__`, `constructor` or `prototype` keys so a later merge changes object behaviour or injects inherited identity fields | The proposal contracts scan the RAW value before zod parses the record (zod would drop an own `__proto__` key silently), so `ModelDecision` and `ToolRequestV2` themselves refuse `__proto__`, `constructor` and `prototype`; `safeParseUntrusted` applies the same scan to any other untrusted value; strict objects reject unknown keys | `platform/src/protocol/common.ts` (`PROTOTYPE_KEYS`, `safeParseUntrusted`), `models.ts`, `tool-envelope.ts` (raw-value preprocess) | AUTH-03 (`protocol/auth03.test.ts` failure injection) | A consumer that merges raw request bodies before parsing bypasses the scan; parse first, then use the parsed value | IMPLEMENTED |
| T-FO-02-03 | Call binding forged from caller-supplied data | S | A caller or model supplies a phone number or arbitrary call id so the platform binds a session to the wrong interaction | `CallBinding.boundBy` accepts only trusted sources (dispatch rule, verified carrier webhook, trusted server lookup); `CarrierInteractionRef` refuses phone-number shaped values; `checkBinding` fails closed on tenant, interaction, state, expiry (independent of TTL), session generation and fencing token | `platform/src/protocol/call-binding.ts` | AUTH-01, AUTH-03, AUTH-04 (`protocol/contracts.test.ts`, `protocol/auth03.test.ts`) | The binding store and issuance (WP-11) and the gateway check (WP-14) do not exist yet; the contract alone authenticates nothing | IMPLEMENTED (contract); producer PLANNED (WP-11) |
| T-FO-02-04 | Protected speech outside an authorized plan | I, E | A plan for a protected fact is issued without authorization or a source, paraphrased, routed to native speech, or a receipt claims audio was emitted after a failed release check | `SpeechPlan` refuses protected-fact classes without `authorizationRef` and a source/receipt, refuses paraphrase for protected and fixed-wording classes, refuses `NATIVE_ALLOWED` outside the low-risk classes; the output-decision digest (`sealSpeechPlan`/`verifySpeechPlanDigest`) binds every field; `AudioReleaseReceipt` cannot record emission unless both enqueue and emission checks passed; a protected-fact plan states no value in its fixed wording (no digit, currency symbol or spelled en/es number outside `{slot}` placeholders, which must equal `slotNames`); clip audio is always recorded as a clip, never as the plan's wording, and `receiptPlanIssues()` checks a receipt against its plan (tenant, call, generation, turn, digest, allowed renderer, clip membership, expiry) | `platform/src/protocol/media.ts`, `digests.ts` | ACT-05, SAFE-02 (`protocol/contracts.test.ts`) | The release guard that enforces this on frames is WP-14; until then no audio path uses these contracts | IMPLEMENTED (contract); producer PLANNED (WP-14) |
| T-FO-02-05 | Partial or cross-subject context presented as complete | I | A context assembler mixes another subject's or tenant's facts, exceeds the classification ceiling, uses a fact for a purpose it is not allowed for, or labels a truncated/conflicting snapshot COMPLETE | `ContextSnapshot` refuses facts from another tenant or subject, subject-less facts above INTERNAL in a subject-scoped snapshot, facts above the ceiling or without the snapshot purpose; a PHI fact always names its subject; a summary claim must cite a fact in the snapshot; any unavailable source, truncation, omission or unresolved conflict forbids COMPLETE; identity/consent/clinical facts must be source-verified | `platform/src/protocol/context-snapshot.ts`, `context-facts.ts` | AUTH-05, DATA-04 (`protocol/contracts.test.ts`) | Field-level row filtering at the source and retrieval re-check remain the assembler's job (WP-24) | IMPLEMENTED (contract); producer PLANNED (WP-24) |
