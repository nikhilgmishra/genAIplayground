# WP-04 proposed threat rows: durable substrate, independent audit and the inbound inbox

Drafted by WP-04 (durable substrate) for the phase B threat-model owner to merge into
[`docs/security/threat-model.md`](../../threat-model.md) (ownership rule "Threat rows" in
`docs/followon/work-packages.yaml`). Row ids are provisional (`T-FO-04-nn`); the merging owner assigns the next
`T-` numbers. Columns follow the threat model's main table. The boundary is the platform's storage, queue and
audit adapters (PostgreSQL / Aurora, DynamoDB, SQS, S3 Object Lock, KMS, Secrets Manager) and the inbound event
ingress. Evidence is Layer 2 against protocol emulators; nothing here runs in AWS (NOT_CONFIGURED).

| T-FO-04-12 | Route evidence recorded out of order across journals | R | PostgreSQL refuses a route event, which goes to the independent DynamoDB journal (possibly from another replica); once PostgreSQL is back the next route event is appended directly, ahead of the older one, so the chain misstates the sequence of routes | Before a direct append the queue checks `audit_deferred`, the DynamoDB journal and memory for the tenant, moves waiting entries into `audit_deferred` and drains them first, or journals the new event behind them; an unreadable journal means "unknown", so the new event is journaled and the tenant's flush waits. A bounded flush pass (or the bounded inline drain) whose DynamoDB read was cut at its bound appends only deferrals it read or that are older than the greatest sort key read, so a newer row never overtakes an unread entry, also when a tampered item or an already-appended entry spends a read slot. Each queue issues strictly increasing deferral times; an event journaled behind older entries is timed after the newest of them (the newest pending DynamoDB item is read newest-first, so another replica's newer entry written with a clock ahead is not overtaken; clamped to 60 s ahead); at an equal time an entry first journaled in DynamoDB goes first | `platform/src/audit/journal.ts` | FO-01-19, FO-15-45, OPS-01 (`src/audit/journal.test.ts` order-across-journals, bounded-flush, inline-drain, re-insert, same-instant and clock-skew tests; `substrate/route-audit-crash.test.ts`: killed replica on read-only PostgreSQL, restarted replica, a replica that cannot read DynamoDB, and a bounded flush with a tampered item on DynamoDB Local) | Order is deferral time; replicas that did not see each other's entries (including an entry put into DynamoDB while a flush pass is between its read and its appends) are ordered only as well as their clocks agree, and after the 60 s clamp is hit a queue's deferral times stay ahead for about a minute. A long DynamoDB read outage delays route evidence reaching the chain (it stays durable and visible as pending) | IMPLEMENTED |
| T-FO-04-13 | One tampered item in the independent journal holds or suppresses route evidence | T, D, R | An insider with write access to the DynamoDB journal table rewrites a pending item (or copies another tenant's item into the partition, or re-keys one to reorder it).
