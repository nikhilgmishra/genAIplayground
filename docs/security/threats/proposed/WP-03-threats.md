# WP-03 proposed threat rows: workspace, dependency set, local composition and runner

Drafted by WP-03 (workspace baseline) for the phase B threat-model owner to merge into
[`docs/security/threat-model.md`](../../threat-model.md) (ownership rule "Threat rows" in
`docs/followon/work-packages.yaml`). Row ids are provisional (`T-FO-03-nn`); the merging owner assigns
the next `T-` numbers. Columns follow the threat model's main table. The boundary is the developer and
CI machine: the pinned dependency set, the Layer-2 composition in [`deploy/local`](../../../../deploy/local/README.md),
the runner (`scripts/vsp/runner.mts`, `Makefile`) and the CI jobs that run them. None of it handles real
patient data or real credentials.

| ID | Threat | STRIDE | Attack path | Mitigation | Enforcement location | Test tags | Residual risk | Status |
|---|---|---|---|---|---|---|---|---|
| T-FO-03-01 | Compromised dependency or image enters the build | T, E | A malicious npm release (direct or transitive), a hijacked install script or a re-tagged container image is pulled into the workspace or the Layer-2 composition | Every manifest specifier is an exact version or `workspace:*` and locked (`check-deps` in CI, `save-exact` in `.npmrc`); CI installs with `--frozen-lockfile`; dependency install scripts do not run except `esbuild` (`pnpm.onlyBuiltDependencies`), the native packages that ship prebuilt binaries are listed in `pnpm.ignoredBuiltDependencies`; `strict-peer-dependencies`; `check-deps` also fails when an installed direct dependency differs from the locked version or declares no licence and warns on copyleft or source-available licences, and `check-deps --inventory` lists every direct dependency with its locked version and licence for docs/INVENTORY.md; images pinned by tag and digest (guards test); pins chosen from releases at least 7 days old and Dependabot proposes updates after a 7-day cooldown, grouped so lockstep packages move together | `package.json`, `.npmrc`, `pnpm-lock.yaml`, `scripts/vsp/runner.mts` (`check-deps`), `deploy/local/services/*.compose.yaml`, `.github/dependabot.yml`, `.github/workflows/ci.yml` | FO-03-14 (`platform/test/integration/_harness/runner.test.ts`, `guards.test.ts`; `deps.test.ts` shows the native packages whose install scripts are ignored still load and run on the CPU) | Transitive ranges were resolved once at lock time; transitive LGPL, MPL and model-licence packages are only warned about (`check-deps`), their obligations are recorded by WP-44; image digests are not signature-verified; the MinIO image is a community build of the upstream source; `pnpm audit` blocks only critical advisories | IMPLEMENTED |
| T-FO-03-02 | Emulators reachable beyond the developer | I, E | An emulator (database, object store, IdP admin, LiveKit API) listens on a public interface with default credentials and is reached from the network | Published ports bind `127.0.0.1` only (checked for every fragment); credentials are generated per checkout into a 0700 state directory, never committed; Keycloak serves HTTPS with a certificate from the checkout's own CA; LiveKit and Valkey require the generated keys | `deploy/local/services/core.compose.yaml`, `scripts/vsp/up.mts` (`ensureState`) | FO-16-01, FO-16-23 (`guards.test.ts`, `health.test.ts` forged LiveKit key and Valkey NOAUTH) | Any local user or process on the host can reach loopback ports; the TLS server key is world-readable inside the 0700 state directory so the Keycloak container can read it | IMPLEMENTED |
| T-FO-03-03 | Emulator calls a real cloud endpoint | I, D | Given a production-format endpoint, an emulator forwards traffic to the real service (Step Functions Local sends to the host named in `QueueUrl`), or an image phones home | Layer-2 renders queue URLs with emulator hosts; the composition holds no real credentials (generated fake keys only); update checks and telemetry are disabled per service (`DISABLE_EVENTS`, `MINIO_UPDATE=off`, `CLAMAV_NO_FRESHCLAMD`, `-disableTelemetry`, `MP_DISABLE_VERSION_CHECK`, `SKIP_SSL_CERT_DOWNLOAD`) | `deploy/local/services/core.compose.yaml`; `platform/test/integration/_harness/workflow.test.ts` (rendering) | OPS-05 (`workflow.test.ts`) | The compose network is not internal (published ports need it), so container egress depends on the host's network policy; an AWS-format URL given to Step Functions Local still makes it try the public endpoint (unauthenticated) | IMPLEMENTED |
| T-FO-03-04 | Emulator or fake results reported as production evidence | R | A test run against emulators, or one that silently used a unit fake, is cited as proof of AWS, carrier or IdP behaviour (OPS-03) | Every Layer-2 test declares its services and the report copies each service's `io.vsp.emulates` and `io.vsp.not-emulated` labels; tests without the declaration fail; a declared service that is not running fails the test with `SERVICE_NOT_RUNNING` (never a skip) and the report lists it under `unavailableServices`; throwaway probe files are excluded from regular runs; static imports of LOCAL FIXTURES, PGlite and in-memory stores are refused; the README records observed fidelity gaps | `platform/test/integration/_harness/` (`layer2.ts`, `setup.ts`, `no-unit-fakes.ts`, `emulation-reporter.ts`) | FO-16-23 (`guards.test.ts`: unit-fake import, unlabelled test, missing service, leftover probe, a service test's meta equals its compose labels; `runner.test.ts`: the written report and emulation summary carry those labels) | A computed relative dynamic import bypasses the import guard, and fixtures reached transitively through a production module are not refused; the service snapshot is taken at global setup, so a service that dies mid-run surfaces as a protocol failure, not `SERVICE_NOT_RUNNING`; emulator divergences (Step Functions Local accepts a callback for an ended execution, MinIO answers 400 where S3 answers 403) mean a passing test is not AWS behaviour | IMPLEMENTED |
| T-FO-03-05 | Local audit evidence destroyed by a teardown | T, R | A routine `make down` (or a CI cleanup) wipes the volumes holding the Layer-2 audit journal and Object Lock bucket without anyone noticing | Volumes are kept by default; `PURGE=1` refuses `io.vsp.data-class: audit` volumes unless `PURGE_AUDIT=1`; the runner takes the destructive options as explicit flags only, and the Makefile forwards `PURGE` / `PURGE_AUDIT` only when they are make command-line assignments (GNU make imports environment variables as make variables, so an exported `PURGE_AUDIT=1` left in a shell is ignored with a notice instead of purging on a plain `make down`); every teardown is recorded with removed and retained volumes | `scripts/vsp/down.mts`; `Makefile` | FO-19-64 (`runner.test.ts`: plain `make down` with `PURGE=1 PURGE_AUDIT=1` exported keeps every volume) | Anyone with Docker access can remove a volume directly; this is local test evidence, not the production audit account (WP-04, WP-39) | IMPLEMENTED |
| T-FO-03-06 | Failing tests reported as passing | R | A wrapper swallows the test runner's exit code, a report is written by an ad hoc command, or a report left by an earlier run is read as the current run's after vitest crashed before writing its own, so CI turns green on failures | The runner returns the tool's own exit code and records it in `vitest-unit.json`; it removes the earlier merged, per-package and integration reports (and the emulation summary) before it runs, reads only reports written by this run, and records a package without a report as failed with no counts (`missingReports`), exiting non-zero even if vitest exited 0; reports are written only by the runner or with `VSP_TEST_REPORT_DIR`, never by ad hoc runs; CI runs `make test-unit` and `make test-integration` | `scripts/vsp/runner.mts`; `platform/vitest.config.ts`; `.github/workflows/ci.yml` | FO-19-67, FO-19-69 (`runner.test.ts`: failing test, crashed run with an earlier passing report, integration run without a report, failing Layer-2 probe suite whose runner exit equals vitest's) | GNU make reports every failing recipe as 2, so only the runner's own code equals vitest's | IMPLEMENTED |
| T-FO-03-07 | Runtime past end of life | T, E | The pinned Node.js line stops receiving security fixes while the platform keeps running on it | `check-runtime` in CI fails a non-LTS or end-of-life line and any mismatch between `.nvmrc`, `engines`, `@types/node`, the image base and CI (every `actions/setup-node` step must read `node-version-file: .nvmrc` and set no `node-version`); it warns 183 days before end of life (Node.js 22 ends 2027-04-30) | `scripts/vsp/runner.mts` (`check-runtime`), `.github/workflows/ci.yml` | FO-03-14 (`runner.test.ts`) | The release schedule is a recorded table that must be refreshed (the check warns when it is a year old) | IMPLEMENTED |
